# Architecture v4 — 分层拦截 + Risk Manager

> 核心思想：tool use check 只是最后一道阀门。在它之上，还有多层审核。每一层管不同的问题，每一层都有明确的介入点。

---

## 0. 为什么不是一个 skill 能解决的

### Skill vs Agent 的区别

| | Skill | Agent (Risk Manager) |
|---|---|---|
| 形态 | 一个 Markdown 文件（prompt） | 独立的执行单元，有自己的 tool/上下文 |
| 输入 | 被主 agent 读进上下文，靠主 agent 自觉遵守 | 接收格式化的输入，独立判断，返回结果 |
| 能不能主动拦 | 不能——只能建议，主 agent 可以不听 | 能——它的返回值就是 allow/deny/ask，平台 hook 会强制执行 |
| 能不能做复杂计算 | 不能——只能靠 LLM 推理 | 能——可以跑脚本、读文件、调用 API |
| 状态 | 无状态（每次重新读） | 有状态（可以记历史、记计数、记预算） |

**结论**：只靠 skill（prompt）拦不住——主 agent 可以忘记、可以忽略。
真正能拦的是 **agent + hook**：hook 触发时调用一个独立的 risk manager agent，它说 deny 就真的 deny。

## 1. 分层架构（从上到下，越往下越硬）

```
Layer 0  意图解析层      LLM 语义判断    5W1H 信息充足度审核
   ↓ 信息不足 → 问用户；信息充足 → 进下一层
Layer 1  范围锁定层      LLM 语义判断    scope.do / scope.dont + 任务预估
   ↓ 超范围 → 问用户；范围内 → 进下一层
Layer 2  Risk Manager   Agent + 脚本    三类风险审核（隐私/token/时间）
   ↓ 低风险 → 放行；中风险 → 问；高风险 → deny
Layer 3  Tool Use Gate  脚本 (hook)     确定性规则（路径/命令/正则）
   ↓ 命中规则 → deny / ask；未命中 → 放行
```

越往下越硬（越不依赖 LLM，越可靠）。
越往上越早发现问题（在还没动手的时候就拦，省 token）。

**为什么 tool use 是最后一道阀门**：
- 上面三层都是"做事之前"的审核——还没调工具，先审"要不要做"
- 最后一层是"动手之前"的审核——工具参数都齐了，最后看一眼"能不能调"
- 上面漏的，最后一层兜底

## 2. Agent 工作流拆解（step-by-step + 介入点）

一个 agent 处理用户请求的完整流程，拆成 7 步。
每一步都标了：谁在做、做什么、介入方式、在哪一层。

```
Step 1  接收用户请求
  做什么：拿到用户的原始输入
  介入：无（刚拿到，还没判断）
  层级：L0 入口

Step 2  意图解析（5W1H 审核）
  做什么：判断用户要什么，信息够不够
  介入：5W1H 信息充足度审核 → 缺什么问什么
  层级：Layer 0（语义层，靠 prompt/skill）
  可能犯的错：过度揣测意图（assume）

Step 3  范围锁定 + 任务预估
  做什么：声明做什么、不做什么；预估时间/token 成本
  介入：向用户 confirm 范围和预估
  层级：Layer 1（语义层，靠 prompt/skill）
  可能犯的错：过度执行（over-execution）、范围蔓延

Step 4  制定执行计划
  做什么：拆分子任务，决定顺序
  介入：子任务循环检测 → 钻牛角尖保护
  层级：Layer 1-2（语义 + risk manager）
  可能犯的错：钻牛角尖（子任务死循环）、过度思考

Step 5  Risk Manager 预审核
  做什么：对"接下来要做的一批动作"做三类风险评估
  介入：隐私风险 / token 消耗风险 / 时间消耗风险
  层级：Layer 2（agent + 脚本）
  可能犯的错：隐私泄露、token 爆炸、超时

Step 6  逐工具调用 + Tool Use Gate
  做什么：调用具体工具（Write/Bash/Edit/...）
  介入：PreToolUse hook → check.py 确定性规则
  层级：Layer 3（纯脚本，最硬）
  可能犯的错：越权操作、force push、删文件

Step 7  结果返回 + 事后回顾
  做什么：把结果返回给用户，检查是否符合 scope
  介入：scope 复核 → 超了就声明
  层级：Layer 0（语义层）
  可能犯的错：交付了 scope 之外的东西
```

## 3. Layer 0 — 5W1H 信息充足度审核

### 是什么

用户说一句话，先系统地过一遍 5W1H，缺什么问什么。
不是"感觉不够就问"，是有固定标准。

### 审核清单

| 维度 | 含义 | 缺了的表现 | 问什么 |
|---|---|---|---|
| **What** | 具体要做什么 | 只有动词（"优化""改进"），没有宾语 | "具体要优化什么？文件/函数/页面？" |
| **Why** | 为什么要做 | 不知道目标，不知道成功标准 | "目标是什么？改完怎么算好？" |
| **Where** | 在哪做 | 没说路径/文件/项目 | "改哪个文件？在哪个项目里？" |
| **When** | 什么时候要 / 时间范围 | 没说优先级、时间预算 | "急吗？大概要花多久你能接受？" |
| **Who** | 给谁用 / 涉及谁 | 不知道受众、权限边界 | "给谁用的？会不会影响别人？" |
| **How** | 怎么做 / 约束 | 没说技术栈、限制条件 | "有什么技术约束吗？用什么语言/框架？" |

### 判定逻辑

```
对用户输入做 5W1H 扫描：
  每个维度打分：明确=2分 / 模糊=1分 / 缺失=0分
  总分 < 6 → 信息不足，必须问
  6 ≤ 总分 < 10 → 信息基本够，但关键维度缺失要问
  总分 ≥ 10 → 信息充足，可以开工
```

### 介入方式

- **纯 prompt 层**：SKILL.md 要求"开工前先过 5W1H"
- **不能脚本化**：因为需要理解自然语言
- **可能漏**：LLM 可能觉得"够了"但实际不够 → 靠 Layer 1 的范围锁定兜底

## 4. Layer 1 — 范围锁定 + 任务预估

### 范围锁定

信息够了之后，先声明：
- **scope.do**：我会做 X、Y、Z
- **scope.dont**：我不会做 A、B、C（比如"不涉及数据库改动""不碰生产环境"）

等用户确认了再动手。

### 任务预估

开工前先给用户一个预估：
- **时间预估**：大概要多久（5 分钟 / 30 分钟 / 2 小时 / 半天）
- **token 预估**：大概要花多少 token（粗略）
- **步骤数预估**：大概要几步

用户觉得"太费了"可以叫停或缩减范围。

### 介入方式

- **纯 prompt 层**：SKILL.md 要求"开工前声明 scope + 预估"
- **state.json 记录**：把 scope 和预估算出来，写进 state.json，给下面几层用
- **可能漏**：LLM 可能忘记声明 → 靠 Layer 2 的 risk manager 检查 state.json 有没有填

## 5. Layer 2 — Risk Manager（核心）

### 是什么

一个独立的 agent（或脚本），在"批量动作开始前"和"每个动作执行前"做风险审核。
它不是 prompt，是**真的能拦**的——它的返回值决定了放行还是拦下。

### 三类风险

#### R1 — 隐私风险 (Privacy Risk)

**审什么**：
- 动作会不会接触用户隐私数据？（对话记录、凭据、个人信息）
- 动作的结果会不会流出本地？（上传、推送、发布、发送）
- 目标位置是不是带远端的目录？（git repo、云盘）

**判定**：
- **高风险**（直接 deny）：把含隐私的内容推送到公网
- **中风险**（双确认）：把内容写入带 git 远端的目录
- **低风险**（放行）：只在本地临时目录读/写

**实现**：
- 脚本部分：check.py 的隐私正则 + git 目录检测（已实现）
- agent 部分：判断"这个动作的结果去哪"（需要语义理解，脚本做不了）

#### R2 — Token 消耗风险 (Token Over-Usage Risk)

**审什么**：
- 这个任务预估要花多少 token？
- 有没有超过用户的预算？
- 有没有可能失控（比如无限循环、递归子任务）？

**判定**：
- **高风险**（deny）：预估超预算 3 倍以上
- **中风险**（ask）：预估接近预算（>70%）
- **低风险**（放行）：在预算内

**实现**：
- 脚本部分：token 计数器（每轮累计，超了触发）
- agent 部分：任务复杂度预估 + 子任务深度限制（最多 3 层嵌套）

#### R3 — 时间消耗风险 (Time Over-Usage Risk)

**审什么**：
- 这个任务预估要花多久？
- 有没有超过用户的时间预期？
- 有没有可能卡死（比如长命令、死循环）？

**判定**：
- **高风险**（deny）：预估 > 2 小时且用户没说"可以长时间跑"
- **中风险**（ask）：预估 > 30 分钟
- **低风险**（放行）：< 5 分钟

**实现**：
- 脚本部分：命令超时设置（默认 30 秒，长命令需用户确认）
- agent 部分：任务时间预估 + 进度汇报（每 5 分钟报一次状态）

### Risk Manager 的形态

**为什么用 agent 形态，不是 skill 形态**：

| | Skill 形态 | Agent 形态 |
|---|---|---|
| 能不能独立判断 | 不能（靠主 agent 读） | 能（自己有上下文、有工具） |
| 能不能计数 | 不能（无状态） | 能（token 计数、时间计数、循环计数） |
| 能不能强制执行 | 不能（主 agent 可以忽略） | 能（hook 调用它，返回值就是命令） |
| 会不会被覆盖 | 会（被后续 system prompt 覆盖） | 不会（独立进程） |

**结论**：Risk Manager 必须是 agent 形态（或脚本形态），不能是 skill 形态。

## 6. Layer 3 — Tool Use Gate（最后一道阀门）

### 是什么

PreToolUse hook 触发时，check.py 跑确定性规则。
这是最硬的一层——纯脚本，不依赖 LLM，不会被覆盖。

### 检查清单（已实现 + 待扩展）

| 规则 | 检查什么 | 命中则 | 实现状态 |
|---|---|---|---|
| 隐私正则 | 内容/路径含密钥、凭据、token | deny | ✅ 已实现 |
| git 目录检测 | Write/Edit 目标在 .git 目录树内 | ask（双确认） | ✅ 已实现 |
| 高危命令 | --force / rm -rf / drop table / gh repo create | ask | ✅ 已实现 |
| 生成无材料 | 生成类工具但 state.json 没 materials | ask | ✅ 已实现 |
| 范围越界 | 工具参数超出 scope.dont | ask | ✅ 已实现 |
| 问题数量限制 | AskUserQuestion 超过 3 个 | ask | ✅ 已实现 |
| 子任务深度 | Agent 嵌套超过 3 层 | deny | ⏳ 待实现 |
| 命令超时 | Bash 命令预估 > 30 秒 | ask | ⏳ 待实现 |
| token 累计 | 本轮 token 超预算 | ask | ⏳ 待实现 |

### 为什么它只是最后一道阀门

- 它只能拦"工具调用时"的问题
- 它拦不了"为什么要做这件事"的问题（那是上面几层的事）
- 它拦不了 thinking block 里的问题（根本没经过工具）

## 7. 钻牛角尖——重新定义 + 解决方案

### 之前的错误定义

以为钻牛角尖 = 问太多问题。
错。问太多问题只是一种表现，而且不一定是坏事（有时该问）。

### 正确定义

**钻牛角尖 = 大任务中遇到一个子任务，主 agent 在那里反复循环、反复试错，没想到可以 spawn 一个子 agent 去专门处理，也没有失败回退措施。**

典型表现：
- 一个 bug 调了 20 轮还没解决，还在试
- 一个调研查了 N 个网页还在继续查，没有结论
- 一个实现写了改、改了写，来回反复

### 为什么会这样

主 agent 的上下文是线性的——它陷进去了就看不到全局。
它没想到："这个子任务我可以外包给子 agent，做不出来就算了，不影响主线。"

### 解决方案（三层介入）

**Layer 1 — 计划层**：
- 拆任务时，子任务如果预估 > 5 步，标记为"可外包"
- 主 agent 先声明"这个子任务我会 spawn 子 agent 做，做不出来就跳过"

**Layer 2 — Risk Manager**：
- 计数器：同一个子任务的重试次数 > 3 → 触发"钻牛角尖警报"
- 警报后：强制 spawn 子 agent，或者向用户报告"这个子任务卡了，要不要跳过"

**Layer 3 — Tool Use Gate**：
- Agent 工具嵌套深度 > 3 层 → deny（防止递归爆炸）
- 每轮 token 累计超阈值 → 强制暂停

### 失败措施（重要）

每个 spawn 出去的子任务必须有：
- **超时**：最多跑 N 步 / N 分钟
- **失败回退**：做不出来就返回"失败 + 原因"，主 agent 继续主线
- **结果验收**：子 agent 返回的结果，主 agent 要检查合不合格

## 8. 任务预估 + 用户确认机制

### 什么时候预估

**Step 3（范围锁定后）**，开工前必做。

### 预估什么

| 项目 | 怎么估 | 单位 |
|---|---|---|
| 步骤数 | 拆成子任务，数一下 | 步 |
| 时间 | 每步 × 预估时间（读=1分钟/写=5分钟/调试=15分钟） | 分钟 |
| token | 每步 × 预估 token（读=500/写=2000/调试=5000） | token |
| 风险等级 | 过一遍 Risk Manager 三类风险 | 低/中/高 |

### 怎么跟用户确认

不是问"可以吗"（太模糊），是给选项：

```
我预估这个任务：
- 大概 5-8 步
- 约 30-60 分钟
- 约 20k-40k token
- 风险：中（会改 3 个文件，不碰生产环境）

A）全开，做完告诉我（推荐）
B）先做前 3 步，做完给我看
C）范围太大，缩减一下
D）不做了

回 A/B/C/D 即可。
```

### 为什么这很重要

- 用户有预期管理——不会突然发现"你花了我 2 小时"
- 用户有控制权——范围太大可以及时叫停
- 减少"过度执行"——先定了范围再动手

## 9. 各层对比总表

| 层级 | 名字 | 管什么 | 形态 | 硬不硬 | 能拦什么 | 拦不住什么 |
|---|---|---|---|---|---|---|
| L0 | 5W1H 审核 | 信息够不够 | prompt/skill | 软 | 过度揣测意图 | 信息够但方向错 |
| L1 | 范围锁定 + 预估 | 做不做、做多少 | prompt/skill | 软 | 过度执行、范围蔓延 | 做的过程中跑偏 |
| L2 | Risk Manager | 三类风险 | agent + 脚本 | 中 | 隐私泄露、token 爆炸、超时、钻牛角尖 | 语义级别的误判 |
| L3 | Tool Use Gate | 工具级越权 | 纯脚本 hook | 最硬 | 删文件、force push、密钥泄露 | 语义级别的越权 |
